## 1. Overview

`nobotrs` is a Rust CLI that detects AI-generated text and lints prose for AI-writing "tells." It is a spiritual full port of the existing Python Claude Code plugin `nobots` (`/home/kwhatcher/projects/nobots`), covering both its detection side and its humanize-writing side — but the humanize side becomes lint-only (flag + suggest, never auto-rewrite), since a standalone Rust binary has no LLM in the loop to steer prose the way nobots' Claude-integrated skill does.

It ships two ways:
1. A standalone, cross-platform Rust binary, installable via `cargo install`, a GitHub Release download, or Homebrew.
2. An Agent Plugins Specification–conformant plugin (the spec formerly known as "Open Plugins," confirmed rebranded as of this research) wrapping that binary, so it works across Claude Code, and any other conformant harness, not just one vendor.

### Goals
- Local-first, offline-capable detection with no mandatory network calls or API keys.
- A spectrum of detection strength: instant deterministic pattern-matching up through heavy local ML, plus optional external commercial APIs, all behind one consistent interface.
- Line-anchored, evidence-backed output — a confidence tier and reasons, never a bare yes/no verdict (carried forward from nobots' existing philosophy).
- A lean default build: a user who only wants pattern + stylometric detection should not need to download any ML model or heavy dependency.

### Non-goals (v1)
- Text generation or auto-rewriting of any kind. `lint` only flags and suggests; it never edits files.
- Full feature parity with `nobots`' `deep_stylometry.py` on dependency-parse-dependent features (dependency distance, whiz-deletion, sentence-relative Biber features, textdescriptives-style coherence). Research found **no viable pure-Rust path** for dependency parsing at all — this is a hard ecosystem gap, not a scoping preference. See §7.
- Bundling prebuilt binaries inside the plugin repository itself. See §6.

## 2. Detection architecture

### 2.1 The `Document` type and `DetectorBackend` trait

```
struct Document {
    raw: String,                      // original file/stdin content, byte-exact
    prose_spans: Vec<Range<usize>>,   // byte ranges of `raw` treated as prose (markdown-aware: excludes code fences, front matter) — Range<usize> is not Copy, iteration needs .clone()/& in the actual impl
    content_type: ContentType,        // Markdown | PlainText | Unknown
}

enum Availability { Ready, NeedsDownload, Unavailable(String) }

enum Error {
    ModelMissing,               // recoverable: run `nobotrs config` to download
    ModelLoadFailed(String),    // recoverable: retry; may indicate a corrupt install
    ChecksumMismatch,           // unrecoverable without reinstalling: pinned hash didn't match (§9 item 2)
    NetworkError(String),       // recoverable: transient, retry
    ConfigError(String),        // recoverable: user must fix config, not a retry
    InternalError(String),      // bug in nobotrs itself
}

impl Error {
    fn is_recoverable(&self) -> bool { !matches!(self, Error::ChecksumMismatch | Error::InternalError(_)) }
}

enum ScoreOutcome {
    Scored(Score),
    Abstained { reason: String },     // e.g. "text too short for burstiness", "non-English text" — not applicable, not a failure
    Failed(Error),                    // backend errored — distinct from abstention, and itself distinguishes recoverable vs. not
}

trait DetectorBackend: Send + Sync {
    fn name(&self) -> &str;
    fn family(&self) -> SignalFamily;              // which independent signal family this backend's vote belongs to (§2.2)
    fn availability(&self) -> Availability;         // model/network readiness, surfaced by `nobotrs config`
    fn score(&self, doc: &Document, deadline: Deadline) -> ScoreOutcome;
    fn score_batch(&self, docs: &[Document], deadline: Deadline) -> Vec<ScoreOutcome> { /* default: map score() */ }
}
```

`Document` replaces a bare `&str` as the trait's input. Evidence needs byte/line offsets into the *original* file for `lint`'s line-anchored output, while stylometric measures need prose-only content — code fences and YAML front matter would otherwise corrupt burstiness/MTLD/readability numbers. Segmentation is markdown-aware at minimum for v1; `content_type` names the strategy explicitly so other formats can be added later without changing the trait shape. `prose_spans` is computed exactly once, at `Document::new()`, and stored — not recomputed per backend; six default backends re-parsing markdown per file would be a real cost on `scan <dir>` over a large tree, and the spec states the O(file-size × 1) cost explicitly to rule that out. `content_type` is determined primarily by file extension (`.md`/`.markdown` → `Markdown`, else `PlainText`); for `detect -`/stdin, where no extension exists, content defaults to `PlainText` unless `--markdown` is passed explicitly — this is a deliberate default (safe, no false-positive code-fence stripping on plain input), not an oversight, and is called out here because it was previously unstated.

`ScoreOutcome` gives a backend a real way to say "not applicable to this input" (`Abstained`) distinct from "something broke" (`Failed`) — matching `check_ai_tells.py`'s own documented behavior, where a family that can't be measured (e.g. burstiness on a short file) simply abstains rather than voting either way. Both `Abstained` and `Failed` are excluded from the vote count in aggregation (§2.4) — neither counts as a "no" — but they are *not* treated identically everywhere: `Failed` additionally surfaces as a `warning` on `detect`'s output (§2.4), because a backend that broke silently is a materially different situation from one that legitimately had nothing to say, and collapsing the two risks a "clean" verdict that's actually just a broken backend (a risk two independent reviews converged on: a stuck/corrupted `classifier` model could otherwise let `detect` report "human-written" when it simply never got to vote). `Error`'s variants are deliberately split so callers (the `config` command, `detect`'s warning surface, log output) can distinguish recoverable conditions (retry, re-download, fix config) from ones that need a reinstall.

`Send + Sync` supports `scan <dir>`'s batch use (§3); `score_batch` gives ML-backed backends (`classifier`, `perplexity`) a seam to batch multiple documents through one model load instead of reloading per file. Model acquisition (downloading and caching weights via `hf-hub`) is out of the trait itself — `availability()` reports readiness, and `nobotrs config` (§3) is what triggers a download.

**One `DetectorBackend` instance produces exactly one family's vote.** `family()` returns a single `SignalFamily`, and `score()` returns a single `ScoreOutcome`/`Score` — the trait does not (and should not) let one implementation multiplex several independent votes. An earlier draft of §2.2 described the `stylometric` tier as "one backend housing four independently-abstaining families," which the trait as written cannot express (`ScoreOutcome` carries one `Score`, which carries one `family`). The fix is at the tier level, not the trait: **a Cargo-feature tier registers one or more backend *instances*, one per family it contributes** — `deterministic` registers a `Vocabulary` backend and a separate `Punctuation` backend; `stylometric` registers a `Burstiness` backend plus several evidence-only backends (§2.2). This keeps `availability()` and `Failed` attribution exact per family, at the cost of slightly more boilerplate than one do-everything struct — `prose_spans` being precomputed once on `Document` (already specified above) means splitting costs nothing extra in practice, since no backend re-parses the document to get its own family's slice of it.

```
enum SignalFamily {
    Vocabulary, Punctuation, Burstiness,   // deterministic + stylometric, voting in v1 (§2.2, §2.4)
    LexicalDiversity, Readability, Compression,  // stylometric, evidence-only in v1 — see §7 item 5
    MlClassifier,                           // classifier tier, voting
    MlPerplexity,                           // perplexity tier, evidence-only — see §7 item 4
    CommercialApi,                          // api tier, voting (collapses all vendors to one vote, §2.2)
}
```

**Deadlines, size limits, and FFI failure modes.** `Deadline` is a **cooperative** budget, not a preemption mechanism — stated precisely because an earlier draft implied otherwise. A `Deadline` value passed into a synchronous `score()` call only has an effect if the callee actually polls it; a backend already blocked inside `llama-cpp-2`'s FFI, a `candle` CUDA kernel, or a `reqwest::blocking` syscall polls nothing, and the deadline expiring changes nothing because there is no running code left to notice it expired. `reqwest`'s 30s HTTP timeout is a real, separate, client-level mechanism that *does* preempt — it's not the same thing as `Deadline`, and the spec should not imply it is. For local ML backends, where a genuine hang (not just slowness) needs to be survivable, `Deadline` alone cannot deliver that — the actual mechanism is either running the backend on a worker thread `detect`/`scan` can abandon (simple, leaks the thread, bounded blast radius) or a subprocess the caller can kill outright (real preemption, more implementation machinery); this spec does not pick between them, but implementation planning must, before claiming `detect` "can't hang" is true rather than aspirational. `detect`/`scan` also enforce a file-size cap (skip files above a configurable threshold, default in the tens of MB, with a warning rather than an OOM) — the same lesson ripgrep and tree-sitter both encode structurally, applied here because `Document::raw` holds a file fully in memory. Separately, and not fully solvable at the Rust level: `classifier` and `perplexity` cross an FFI boundary into C/C++ ML runtimes (candle's CUDA/Metal backends, `llama-cpp-2`), and a hard crash there (segfault, abort) is not a catchable Rust panic — `catch_unwind` cannot intercept a signal. This is accepted as a stated v1 limitation, not solved: input validation before handing text to these backends is the primary mitigation, not exception handling. Running multiple ML backends concurrently (e.g. `scan <dir>` parallelizing across files with `classifier` enabled) additionally needs a concurrency model this spec does not prescribe — `candle`'s GPU backends are not safely shared across threads by default, so implementation planning must pick one of: per-thread model instances (simple, costs RAM per thread), a mutex around inference (simple, serializes GPU work), or a dedicated inference thread with message-passing (best throughput, more code) before `scan` is allowed to parallelize the ML tiers.

### 2.2 The five backend tiers and signal families

Backends are grouped into independent **signal families** for aggregation purposes (§2.4) — a different axis than the Cargo feature-flag grouping below, and the two must not be conflated. A Cargo feature *tier* registers one or more backend *instances*, one per family (§2.1) — the table's "Signal family/families" column lists which backend instances a tier contributes, not a claim that one struct produces several votes.

**Only three of the following families vote in v1: `Vocabulary`, `Punctuation`, `Burstiness`.** This is a correction from an earlier draft, which promoted `LexicalDiversity`, `Readability`, and `Compression` to full voting status. Re-checking `check_ai_tells.py` directly: the Python computes MTLD, Flesch-Kincaid, and the LZMA compression ratio, but appends them to its output under the literal heading *"Additional context (informational, not independently calibrated)"* — they were deliberately excluded from the vote because nobody had calibrated them, the same reason §7 item 4 already withholds `MlPerplexity`'s vote. There is no principled reason those three should have been promoted in the Rust redesign while `MlPerplexity` wasn't; this draft applies the same treatment to all four uniformly (§7 item 5). The practical effect: the default (`deterministic` + `stylometric`) build has **three** voting families, not six, so `QUORUM = 2` is the same 2-of-3 bar the Python actually validated in production — not a new, looser bar needing separate justification (§2.4).

| Tier | Feature flag | Default? | Backend instances (family — voting?) | What it does | Key crates |
|---|---|---|---|---|---|
| **deterministic** | *(always on)* | Yes | `Vocabulary` backend (voting); `Punctuation` backend (voting) | `Vocabulary`: exact tell-word / tell-phrase matching, data-driven from the separately-licensed tell dictionary (§11) rather than hardcoded in the binary, seeded from `check_ai_tells.py`'s existing lists. `Punctuation`: em-dash/mechanical-punctuation density counting — code-only, no dictionary representation (§11.2), since it's a count over the text, not a match rule | `aho-corasick` (tell-words, linear time at scale), `regex` (tell-phrases with wildcards), `unicode-segmentation` (sentence/word boundaries) |
| **stylometric** | *(always on)* | Yes | `Burstiness` backend (**voting**); `LexicalDiversity`, `Readability`, `Compression` backends (**evidence-only in v1**, §7 item 5) | Burstiness: sentence-length stdev/mean, gated on ≥5 sentences (Python's own floor, `check_ai_tells.py:38`). Lexical diversity: hand-rolled MTLD, gated on `MIN_WORDS_FOR_DIVERSITY` (50 words, Python's floor). Readability: hand-rolled Flesch-Kincaid (see §10), and every stylometric family besides burstiness is additionally gated on `MIN_WORDS_FOR_STATS` (150 words, Python's floor) — ported forward explicitly here rather than left as the vague "text too short" placeholder an earlier draft used. Compression: LZMA compression-ratio proxy plus entropy-per-token (bundled into this backend's evidence, not a separate family). Language-tuned features (readability, some lexical-diversity assumptions) are gated behind a `whichlang` check; non-English input abstains rather than scoring incorrectly | `unicode-segmentation`, `statrs`, `lzma-rs` (pure-Rust LZMA — see §10 for why not `xz`), `whichlang` |
| **classifier** | `classifier` | No | `MlClassifier` backend (voting) | Single-pass fine-tuned AI-text classifier inference (DeBERTa-v3-style) via `candle-transformers::debertav2` — **module confirmed to exist and architecturally match this use case; compatibility with the specific `desklib/ai-text-detector-v1.01` checkpoint is unconfirmed, see §9 item 1** | `candle` + `candle-transformers::debertav2`; `ort` (ONNX Runtime) as documented fallback; `hf-hub` for weight download |
| **perplexity** | `perplexity` | No | `MlPerplexity` backend (**non-voting/experimental in v1**, see §7 item 4) | Twin-model zero-shot perplexity ratio (Binoculars/Fast-DetectGPT style); reports the raw cross-perplexity ratio as evidence but does not participate in quorum aggregation until calibrated (§8). Validated model pairs are memory-heavy (~8–10GB RAM); no smaller validated pair was found in research | `candle` or `llama-cpp-2` (GGUF quantization); `hf-hub` |
| **api** | `api-clients` | No | `CommercialApi` backend (voting; one family for the whole tier, regardless of vendor count) | Optional external commercial detector calls, user-supplied API key required | `reqwest` (`blocking` feature), one client module per vendor (Sapling, GPTZero, Copyleaks, Pangram) |

`classifier` and `perplexity` are separate flags (a user can enable one without the other). `api-clients` is one shared flag gating all four vendor clients, since they share the same `reqwest` dependency and trait shape — but at the signal-family level (§2.4), all configured API vendors collapse into a single `CommercialApi` vote, not one vote per vendor, since commercial detectors are often trained/calibrated on overlapping data and are not independent signals. (`Burstiness` and `Readability` aren't perfectly independent of each other either — mean sentence length is a term in the Flesch-Kincaid formula and the denominator of burstiness — but demoting `Readability` to evidence-only above already removes it from the vote; the calibration pass in §8.1 is where any remaining cross-family correlation among voting families gets measured empirically rather than assumed away.)

A `full` meta-feature enables `classifier` and `perplexity` — the local ML tiers — for users who want maximum local coverage in one build. **`full` deliberately excludes `api-clients`**: a convenience build flag should not silently enable third-party data egress once a user later configures a key. Commercial API calls always require the separate, explicit `api-clients` flag.

**How `aho-corasick` word-hits and `regex` phrase-hits combine into one vote:** both feed the single `Vocabulary` family, not two separate families — this mirrors `check_ai_tells.py` exactly, where tell-words and tell-phrases were already one combined "vocabulary" signal, not split. A word hit and a phrase hit are not weighted differently by match type; the `Vocabulary` family's vote strength (`Suspicious`/`Strong`) is a hit-count threshold across both matchers combined, tuned against the evaluation corpus (§8.1) like every other threshold in this design — not hand-picked, and not something this spec fixes a specific number for.

### 2.3 `Score` — the common result type

```
struct Score {
    backend: String,
    family: SignalFamily,        // which independent signal family this vote belongs to (§2.2)
    human_probability: f32,      // 0.0 (certainly AI) .. 1.0 (certainly human) — a reporting value, not the aggregation currency
    confidence: ConfidenceTier,  // Low | Medium | High
    evidence: Vec<Evidence>,     // line/offset-anchored into Document::raw where applicable
}

struct Evidence {
    raw_offset: Range<usize>,     // byte range into Document::raw — what an editor/lint annotation points at
    prose_offset: Range<usize>,   // byte range into the matched prose span — what stylometric measures computed over
    line: u32,
    column: u32,
    matched_text: String,         // the actual substring that triggered this evidence
    severity: Severity,           // Low | Medium | High
    suggestion: Option<String>,   // populated from the dictionary (§11.3) for deterministic hits; None otherwise (§3)
}
```

`human_probability` is the canonical continuous representation for display and JSON output (§3). Pangram's API returns continuous fractions natively; the other three commercial vendors and the deterministic/stylometric backends return coarser labels or thresholds, which map onto fraction *bands* rather than exact points — deliberately chosen so no backend's precision is silently lost on the way in. **This float is reported per backend but is not what aggregation operates on** — see §2.4.

**`human_probability` must never be NaN or infinite.** `f32` permits both, and neither is a meaningful probability. This is stated as a hard contract, not a guideline: a backend that emits `NaN` produces a value where every comparison (`> 0.5`, `< 0.5`, `== 0.5`) is false, which would silently corrupt any thresholding logic without a test ever catching it, since nothing panics. The aggregation boundary validates/clamps this at construction (implementation detail for planning; the spec's commitment is the contract, not the exact enforcement mechanism). Relatedly: `f32` does not implement `Ord` (only `PartialOrd`), precisely because of `NaN`. Anywhere this spec's aggregation or output logic sorts or ranks `Score`s by `human_probability`, it must use `f32::total_cmp` or explicit `partial_cmp` handling — never assume `Ord` is available.

`Evidence`'s two offset fields are deliberately distinct: `raw_offset` is what `lint` points an editor at (position in the file the user actually wrote), while `prose_offset` is the position within the extracted prose span a stylometric backend actually measured — these differ whenever code fences or front matter precede the match, and conflating them would point evidence at the wrong byte in one direction or the other.

### 2.4 Ensemble aggregation

Aggregation operates on **signal families** (§2.2), not on backends and not directly on `human_probability` floats. This is a deliberate correction from an earlier draft of this spec, which claimed to carry forward `check_ai_tells.py`'s quorum rule without noticing that the Rust redesign changed what the rule counts: the Python votes by family (`vocabulary`, `punctuation`, `burstiness`); a naive Rust port that voted by *backend* would silently make the default two-backend build's `QUORUM = 2` mean unanimity instead of "2 of several agree."

Each signal family, for a given `Document`, produces one discrete vote: `Abstain | Suspicious | Strong` — mirroring `check_ai_tells.py`'s own three-way per-family vote. The vote is discrete, not continuous; the Python original never produces a continuous probability either, and `human_probability` (§2.3) is reported alongside the vote for display, not derived into it. A family whose backend returned `ScoreOutcome::Abstained` or `ScoreOutcome::Failed` for this document contributes no vote at all — excluded from both numerator and denominator, never counted as a "no."

A top-level `detect` command runs every enabled backend, collects one vote per non-abstaining family, and fires a verdict when at least `QUORUM` families agree at `Suspicious` or stronger — the same principle `check_ai_tells.py` uses (an earlier "any one family over threshold" rule produced false positives in the Python version; this quorum is the fix that lesson led to).

**`detect`'s output is a `verdict` plus a separate `warnings` list, not just a verdict.** `verdict` is one of `Flagged` (quorum met), `Clean` (quorum not met, and enough families were able to analyze the input for that to be a meaningful conclusion — see the `Inconclusive` case below), or `Inconclusive` (too few families could analyze the input at all for `Clean` to mean anything). Separately, the output carries `warnings: Vec<{ family: SignalFamily, error: Error }>` populated whenever a family's backend returned `Failed`. A `Clean` verdict with a non-empty `warnings` list means something different from a `Clean` verdict with an empty one: the former is "quorum wasn't met, but also not every family that should have voted actually could" (e.g. a corrupted `classifier` model, a config with `api-clients` enabled but no working network), and both `nobotrs detect`'s human output and its `--format json` output must surface that distinction rather than collapsing both cases into an indistinguishable "clean." This closes a real gap: without it, a broken backend and a genuinely clean document produce byte-identical `detect` output.

**`Inconclusive` closes a second, related gap: `Failed` and `Abstained` are handled, but universal legitimate abstention wasn't.** `check_ai_tells.py` gates its statistics on explicit floors (`MIN_WORDS_FOR_STATS = 150`, `MIN_WORDS_FOR_DIVERSITY = 50`, ≥5 sentences for burstiness — all ported into §2.2's per-family abstention rules above) precisely because a family computed on too little text is noise, not signal. An earlier draft carried the floors forward as abstention *reasons* but not into the verdict itself: a 40-word file where most families abstain "for cause" and only one or two happen to vote would previously report either `Flagged` (quorum met on a sample too small to mean anything) or `Clean` (indistinguishable from a document that was actually, thoroughly analyzed) — both wrong. The rule: track `votes_cast` = the count of families that returned `ScoreOutcome::Scored(_)` for this document, regardless of vote strength (a family that scored and found nothing suspicious still completed a real analysis; only `Abstained`/`Failed` are non-participation). If `votes_cast < QUORUM`, the verdict is `Inconclusive` regardless of what the families that did vote said — even if every single one of them voted `Strong`, there aren't enough independent signals present for that to be trustworthy. Only when `votes_cast >= QUORUM` does the ordinary `Flagged`/`Clean` distinction apply.

**The default build's quorum is the same 2-of-3 bar the Python actually validated, not a new one.** The default (`deterministic` + `stylometric`) build now has exactly three *voting* families — `Vocabulary`, `Punctuation`, `Burstiness` (§2.2) — matching the Python's own voting set exactly, so `QUORUM = 2` here is the identical bar the Python shipped with in production, not a novel one needing separate justification. (An earlier draft of this paragraph claimed the opposite — that six families made `QUORUM = 2` "explicitly unanimity" — while the very next sentence in that draft described it as "a much looser bar"; that was a direct self-contradiction, a leftover from before §2.2's voting-family correction above, and is removed here rather than reconciled, since the corrected family count makes the contradiction moot.) `QUORUM` remains tunable via config, not hardcoded, and its value is still a starting point pending §8.1's calibration pass — the "same as the Python" framing is a validated starting point, not a claim that no retuning will ever be needed.

`CommercialApi` contributes exactly one vote regardless of how many vendors are configured (§2.2): computed as a majority (or, if configured, max-confidence) verdict across whichever vendors are active, so correlated commercial signals cannot out-vote the local families by sheer vendor count.

`MlPerplexity`, `LexicalDiversity`, `Readability`, and `Compression` do not vote at all in v1 — see §7 item 4 (perplexity) and §7 item 5 (the other three) and §8.

**A maximally-confident `MlClassifier` vote is capped at the same weight as any other family's vote — not resolved as "obviously fine," stated as an open calibration question.** Votes are `Abstain | Suspicious | Strong` with no weighting by `ConfidenceTier` (below), which means a fine-tuned classifier returning `human_probability: 0.01` (about as confident as a calibrated model gets) casts exactly one `Strong` vote — the same weight as `Punctuation` tripping on three em dashes. Under `QUORUM = 2`, a user who enabled `classifier`, downloaded the weights, and got an unambiguous single-model verdict still sees `Clean` unless a second family agrees. The quorum rule exists to stop *weak heuristics* from firing alone (`check_ai_tells.py`'s own stated rationale); that rationale doesn't obviously transfer to a corpus-calibrated classifier, and this spec does not resolve the question by default — it states it explicitly instead. **Decision, gated on §8.1:** a solo `Strong` vote from `MlClassifier` is permitted to meet quorum on its own *only if* the evaluation corpus validates that the classifier's calibration supports it at the target false-positive rate; until that validation exists, `MlClassifier` votes like every other family, with no default override. This is named here so the choice is deliberate, not whatever an implementer happens to pick while heads-down in `score()`.

`ConfidenceTier` on each `Score` (§2.3) is reported for display but does not currently weight the ordinary vote; a family's vote is binary-strength (`Suspicious`/`Strong`) regardless of its confidence tier, except for the `MlClassifier` override above, which is the one place confidence is load-bearing to the verdict rather than purely informational. Confidence-weighted voting more broadly is a plausible v2 refinement once the evaluation corpus (§8) exists to validate it actually improves accuracy rather than adding an untested knob.

## 3. CLI surface

```
nobotrs detect <path|->            # score a file or stdin (- follows UNIX convention, e.g. `cat f | nobotrs detect -`), quorum ensemble verdict + confidence tier (§2.4)
nobotrs lint <path>                 # line-anchored tells report: every backend's evidence, unfiltered by quorum
nobotrs scan <dir>                  # batch lint across a directory (e.g. CI use); deterministic + stylometric only by default
nobotrs config                      # manage API keys, model downloads, enabled backends, availability status
```

`-` (not a `--stdin` flag) is how `detect` reads from stdin, matching the standard UNIX convention used by `grep`, `ripgrep`, and most composable CLI tools — a bespoke `--stdin` flag would duplicate behavior most users already expect from the dash.

`detect` applies the §2.4 quorum and reports one aggregated `verdict` (`Flagged`/`Clean`/`Inconclusive`) plus `warnings` (§2.4). `lint` does **not** apply quorum — it reports every backend's raw evidence (including sub-quorum, single-family hits) so a human can see everything a `detect` verdict would have suppressed; this is a deliberate difference, not an oversight, and it's the reason the plugin's ambient hook (§6) invokes `detect`, not `lint` — an ambient scan that fired on any single tell-word hit would defeat the entire point of the quorum system at the one place users experience it passively.

**`scan <dir>` is a batch `detect`, not a batch `lint`** — an earlier draft described it both ways in different places, which is resolved here in `detect`'s favor: CI, `scan`'s stated primary consumer, needs a pass/fail signal per file, not an unfiltered per-file evidence dump. `scan` runs the `deterministic` + `stylometric` tiers by default (fast, no model downloads, safe for unattended CI) and produces one `detect`-equivalent verdict per file plus an aggregate summary; `classifier`/`perplexity`/`api-clients` participate only when explicitly enabled via `--features`/config, since a batch directory scan is exactly the case where unbounded model-loading or API cost is most likely to surprise a user. `scan <dir>` applies default ignore patterns (`.git/`, `node_modules/`, common binary/compiled-artifact extensions — the same category of lesson ripgrep's default ignore list encodes) and prints a summary line (files analyzed / skipped / excluded / flagged / inconclusive) rather than silently reporting "clean" on a directory that was mostly vendored binaries and never actually analyzed anything.

**Suggested fixes** (in `lint` output) apply to deterministic tell-word/tell-phrase hits, sourced directly from the tell dictionary's `suggested_replacements` field (§11.3) — e.g. "delve" → "look into"/"start" — rather than being generated or templated by nobotrs itself. Stylometric flags (low burstiness, low MTLD, compression-ratio anomalies) get diagnostic explanation but not a templated fix — there's no single correct rewrite for "your sentence-length variance is low," only general guidance. `Evidence` (§2.3) carries a `suggestion: Option<String>` to reflect this: `Some` (populated from the dictionary) for deterministic hits, `None` for stylometric flags where no specific fix applies.

- Argument parsing: `clap` (derive API).
- Human output: colored terminal via `owo-colors`, **with its `supports-colors` Cargo feature explicitly enabled** — verified against the crate's own source: `owo-colors` ships with no default features at all, and `NO_COLOR`/`FORCE_COLOR` detection is entirely absent unless `supports-colors` is turned on. Stating this explicitly here because the earlier draft's "(respects `NO_COLOR`)" was true only conditionally, not by default.
- Machine output: `--format json` via `serde`/`serde_json`, for CI/scripting. The JSON shape carries a `schema_version` field from v1 onward; breaking changes to the output shape bump it independently of the crate's own semver, since CI consumers parse the JSON contract, not the crate API. **The concrete v1 schema (exact field names/shapes per command) is an implementation-planning deliverable, not specified here** — §2.3's `Score`/`Evidence` struct sketches are its foundation, but the actual wire format, and what a terminal `lint` report visually looks like, need a UX pass during planning; this spec has been architecturally reviewed, not UX-reviewed, and that gap is stated explicitly rather than left implicit.
- Exit codes: `0` = `Clean` (analyzed, quorum not met, no warnings), `1` = `Flagged` (quorum met), `2` = tool failure **or** `Clean`/`Flagged` with a non-empty `warnings` list (any enabled backend returned `Failed`), `3` = `Inconclusive` (too few families could analyze the input for a verdict to mean anything, §2.4). An earlier draft defined only three codes and never stated what a non-empty `warnings` list did to the exit code — meaning a corrupted `classifier` model could produce `verdict: Clean` at exit `0`, a CI pipeline passing green on a silently broken backend, which is precisely the failure mode §2.4's `warnings` mechanism exists to surface and this exit-code gap would have hidden from the one consumer (CI) that never reads the human-readable output. Mapping *any* `warnings` to exit `2` (not `0`/`1`) is the deliberately conservative default — noisier on a flaky network than a `--strict`-style opt-out might be, but silent-pass-on-broken-backend is the worse failure mode for a CI gate. See §6 for how the plugin's `PostToolUse` hook wrapper translates these.

### 3.1 v1 definition of done

The primary v1 user is an individual developer or a CI pipeline checking prose files (READMEs, docs, PR descriptions) for AI-writing tells — not a platform team running accusation-grade audits at scale; that use case needs the calibration rigor of §8.1 before it's responsible to support, and this spec does not claim v1 is ready for it. The minimum "must work" scenario: `nobotrs detect README.md` on the default build (no feature flags, no model downloads) returns a verdict in well under a second, fully offline. v1 is ready to ship when: the default build's measured false-positive rate on the §8.1 evaluation corpus is below its stated target — **that target is itself not yet set** (§8.1 calls it an open product decision), so this criterion depends on a number this spec doesn't fix; readers of this section shouldn't take it as self-contained — all Blocker items from every review round are resolved, and `cargo install nobotrs` / the Homebrew tap both work end-to-end on a clean machine. Without this stated somewhere, the spec's five tiers and four commands have no stopping rule for when implementation is "done enough" — this section is that stopping rule.

## 4. Configuration and secrets

- Config file: resolved via the `directories` crate, **not a hardcoded Unix path** — the earlier draft's `~/.config/nobotrs/config.toml` is the Linux path only. Actual resolved paths per platform:

  | Platform | Config path |
  |---|---|
  | Linux | `~/.config/nobotrs/config.toml` |
  | macOS | `~/Library/Application Support/com.nobotrs.nobotrs/config.toml` |
  | Windows | `C:\Users\<user>\AppData\Roaming\nobotrs\nobotrs\config.toml` |

  Documentation and `nobotrs config`'s own help text must reference "your platform's config directory" (or print the resolved path directly), not the Linux path specifically. File permissions are restricted on every platform, but the mechanism is platform-specific: `0600` on Unix, an equivalent ACL restriction on Windows — stated generically here because "tightened to `0600`" (the earlier wording) is meaningless on Windows.
- Precedence for API keys: environment variable → optional OS keychain via the `keyring` crate → config file. This mirrors the precedence pattern used by tools like `gh` and `aws-cli`, and — corrected from an earlier draft, which put the keychain *last* — puts the plaintext config file at the bottom of the chain rather than the most-protected store: a user who moves a key into the keychain but forgets to also delete it from `config.toml` should get the keychain's value, not silently keep using the plaintext copy with no indication anything's wrong. `keyring` remains opt-in (not required) rather than a mandatory part of the chain, because its Linux backend depends on the Secret Service D-Bus API (via `zbus`) — commonly absent on headless CI runners with no D-Bus session running, where it would fail with a platform-specific error a non-expert user can't easily diagnose. CI users should rely on the environment-variable method, which has no such dependency and sits first in precedence regardless of whether `keyring` is configured at all.
- No commercial API is ever called without an explicit key configured for that specific vendor — enabling the `api-clients` feature at build time does not itself send any data anywhere.
- API keys must never appear in log output, error messages, or `Debug` representations — and this needs to be enforced at more surfaces than "don't log the key directly": `reqwest::Error` can include the request URL, so vendor clients that pass a key as a query parameter must sanitize the URL before it's ever logged; a panic or `unwrap()` inside a vendor client's request-building code must not let the default panic hook print a key held in a local variable; any future `--verbose`/`--debug` flag must redact secret values in its output by design, not by later patch; and error messages must never echo a misconfigured secret's *value* back to the user (echoing the *variable name*, e.g. "SAPLING_API_KEY is not set," is fine and helpful — echoing what the user typed for it is not). This is stated explicitly now, before four vendor client modules exist, because it is a well-known, generic Rust footgun that is cheap to prevent up front and expensive to retrofit across every client afterward.

## 5. Packaging and distribution

- **Release pipeline:** `cargo-dist` builds and publishes per-platform binaries (Linux x86_64/aarch64, macOS x86_64/aarch64, Windows x86_64) to GitHub Releases, auto-generates a Homebrew tap formula, and publishes to crates.io on tag push. `cargo-dist`'s checksum generation is enabled for every release artifact, and the auto-generated Homebrew formula pins a SHA256 checksum — a user downloading a GitHub Release binary has a way to verify it wasn't tampered with in transit. `cargo install nobotrs` trusts the full dependency tree at build time; for a tool whose entire purpose is resisting adversarial input, an unaudited dependency tree is a real (if generic) supply-chain risk — CI runs `cargo deny` (or equivalent dependency-audit tooling) as a stated policy, not an aspiration.
- **Binary size discipline:** default build (deterministic + stylometric only) targets roughly 10MB; `classifier`/`perplexity` features add candle (~50-80MB) or ONNX Runtime (~100-150MB) — these are documented as separate, explicit install paths, not silently bundled into a bloated default. `api-clients` adds negligible size (`reqwest` alone, no ML runtime). This ~10MB figure is an aspiration, not a fact, until it's a CI-asserted budget: `clap` + `serde` + `regex` + `aho-corasick` plus an embedded dictionary land in that neighborhood only with deliberate `[profile.release]` settings (`lto = true`, `strip = true`, an appropriate `opt-level`) — CI should fail the build if the default binary exceeds a stated size threshold, not just hope the target holds as dependencies accrue over time.
- **Explicitly not v1 scope:** Nix flake packaging, a `cargo nobotrs` subcommand alias, and a WASM build target are all plausible future distribution channels with no v1 commitment — `cargo-dist`, crates.io, and Homebrew are the only channels this spec commits to. Named here so the absence reads as a scope decision, not an oversight.

## 6. Plugin packaging (Agent Plugins Specification)

- Manifest at `.plugin/plugin.json` (generic) with a `.claude-plugin/plugin.json` vendor copy for Claude Code's own discovery path, per the spec's documented vendor-precedence rule.
- `skills/detect-ai-writing/SKILL.md` — portable across any conformant harness.
- `hooks/hooks.json` — a `PostToolUse` hook wiring the ambient scan-on-write UX, invoking **`bin/nobotrs detect --format json`** (§3) — **not `lint`**, corrected from an earlier draft that wired the hook to `lint`, which explicitly bypasses quorum (§3) and would have made the ambient scan fire on a single tell-word hit, the exact false-positive behavior the whole quorum system exists to prevent, defeated at the one integration point users experience passively. The exit-code mapping needs re-verification against Claude Code's current hooks documentation before implementation locks it in — an earlier draft asserted a specific mapping (exit 1 → non-blocking feedback, exit 2 → block) that doesn't match what `check_ai_tells.py`'s own docstring says about the *existing* Python hook's behavior: its docstring states it "exits 2 (stderr fed back to Claude)" specifically *on findings*, and its "fails open" property (a bare `except: return 0`) is about **hook bugs**, not about findings at all — those are two different concerns the earlier draft's mapping conflated. Whatever the correct current mapping is, the requirement stands regardless: the ambient scan must never *block* a write (matching the Python's behavior on findings, which surfaces feedback but doesn't block), and `nobotrs`'s own exit codes (§3) — including the new `2` (warnings) and `3` (`Inconclusive`) states — need their own explicit mapping into whatever the hook protocol's current codes actually mean, not just `0`/`1`. **This component is Claude-Code-only in practice** (OpenCode and Pi use their own native JS/TS event systems rather than consuming `hooks.json`) — the same caveat nobots' own README already documents for its Python hook, carried forward rather than newly introduced.
- `bin/nobotrs` — a thin wrapper, **not a bundled binary**, and **not a single Bash script** — Bash alone doesn't cover Windows without WSL/Git Bash, and this spec commits to real cross-platform support (§5), so a Bash-only wrapper would be a silent gap for Windows-native users. v1 ships an `sh`/`bash` wrapper for Linux/macOS and a `.ps1` companion for Windows (both doing the same search), or, if implementation planning finds that simpler to maintain, a tiny statically-linked Rust binary that does nothing but the search-and-locate logic (same idea `nab`/`genasis` use, minus the shell-vs-PowerShell duplication). Search order (in order): an env var override, `PATH`, well-known install directories per platform (`~/.cargo/bin`, `/opt/homebrew/bin`, `/usr/local/bin` on Unix; `%USERPROFILE%\.cargo\bin` on Windows) — resolved generically the same way §4's config path table is, not hardcoded to one platform. If multiple installed versions are found (e.g. both a Homebrew and a `cargo install` copy), the wrapper picks the first match in search order and this is stated as the resolution rule, not left to be environment-dependent surprise. On failure it prints an actionable install message: the exact `cargo install` command, the `brew install` command, and a direct GitHub Release download URL, all as plain text (not tool-specific formatting). No plugin repo in the ecosystem was found bundling actual per-platform binaries in-repo — the two real examples found (`nab`, `genasis`) both locate-or-download instead. Claude Code has no `postInstall` hook to lean on for automatic fetch-on-install (the relevant feature request, anthropics/claude-code#9394, is closed as not-planned), so "locate or fail with clear instructions" is the v1 behavior; an automatic-download wrapper is a plausible v2 addition once the binary is actually published via `cargo-dist`. Plugin installation (`/plugin install`) does **not** trigger binary installation — the two are manual, separate steps in v1, and the wrapper's failure message is what bridges that gap.

## 7. Explicit v1 scope-outs and known gaps

These are carried in the design deliberately, not silently dropped:

1. **Dependency-parse-dependent stylometric features** (dependency distance, whiz-deletion, sentence-relative Biber features, textdescriptives-style coherence). No pure-Rust dependency parser exists anywhere in the ecosystem (confirmed by dedicated research, not just "none found easily"). Out of scope for v1. A future option, not committed to: an optional Python sidecar shelling out to the existing `deep_stylometry.py`, degrading gracefully when absent.
2. **POS-tag-dependent features** (POS proportions, function/content-word ratio, hedges, amplifiers, nominalizations). The only real pure-Rust option (`postagger.rs`) is unproven/low-maintenance; the higher-confidence option (`rust-bert`'s MobileBERT tagger) only becomes "free" if `tch-rs` is already a dependency for other reasons. Deferred; revisit once the `classifier` tier's ML dependency choice is settled empirically.
3. **Any text generation or auto-rewrite capability.** Confirmed out of scope per product decision — lint-only.
4. **`MlPerplexity` as a voting signal family** (§2.4). GGUF quantization shifts the logit distributions Binoculars' published calibration threshold was tuned against, and there is no data yet to refit that threshold for the quantized numerics nobotrs would actually ship. `perplexity` still ships in v1, feature-gated, and still reports its raw cross-perplexity ratio as evidence — the product decision to include the tier stands — but it is explicitly non-voting until the evaluation corpus (§8) exists to calibrate it properly. **This non-voting status must be impossible to miss, not a footnote a user has to already know to look for**: a user who enables `perplexity` has downloaded 8-10GB of model weights, and if `nobotrs detect`'s output doesn't make it obvious that the tier they paid that cost for isn't influencing the verdict, that's a bad experience masquerading as a subtle design nuance. Both `nobotrs detect` and `nobotrs config`'s output must state plainly, unmissably: "Perplexity tier: experimental, evidence-only, does not affect verdicts" — this is a UX requirement carried into implementation, not just an internal aggregation rule.
5. **`LexicalDiversity`, `Readability`, and `Compression` as voting signal families** (§2.2, §2.4). An earlier draft promoted all three to full voting status in the Rust redesign. Re-reading `check_ai_tells.py` directly: the Python computes exactly these three measures (MTLD, Flesch-Kincaid, LZMA ratio) and explicitly withholds them from the vote, appending them under the literal heading "Additional context (informational, not independently calibrated)." The identical reasoning §7 item 4 applies to `MlPerplexity` — non-voting until calibration exists to justify voting status — applies here and wasn't applied in the earlier draft; that inconsistency is the correction this item makes. All three ship in v1, evidence-only, exactly like `MlPerplexity`; §8.1's calibration pass is what would promote any of them to voting, not a default assumption that they already carry independent signal.

(The `stylometry` (ian-nai/rust_stylometry) crate previously listed here has been dropped — it isn't referenced anywhere in §2.2's actual crate list, and its unverified license created an unnecessary contradiction with §10. If a future need for classic authorship-analysis statistics arises, the same functionality can be hand-rolled the way MTLD and Flesch-Kincaid already are.)

## 8. Testing strategy

- Unit tests per backend against known-AI and known-human text fixtures (the existing `nobots` rubric and any of its test fixtures are a starting corpus).
- The quorum-aggregation logic gets dedicated tests for its false-positive-avoidance behavior (the specific bug class it was designed to prevent in the Python version).
- API-client backends are tested against mocked HTTP responses — no live network calls in the test suite, no requirement for real API keys to run `cargo test`. Mocked responses can't catch upstream vendor schema drift over time; this needs a documented periodic manual re-verification note, not just a one-time integration test.
- `classifier` and `perplexity` backends need a smaller, separate integration-test tier gated behind their own feature flags, since they require model downloads and real compute — not part of the default `cargo test` run.
- CI runs a minimal feature-flag matrix rather than full combinatorial coverage: `default`, each of `classifier`/`perplexity`/`api-clients` isolated, and `full`. This catches feature-interaction bugs without an exponential build matrix.
- Hand-rolled stylometric formulas (MTLD, Flesch-Kincaid — §10) are unit-tested against published reference test vectors (known texts with known, citable MTLD/Flesch-Kincaid scores), not just checked for internal self-consistency — a hand-rolled formula that's internally consistent but diverges from the standard algorithm is a correctness bug that self-consistency tests alone won't catch.
- Every dictionary (§11) regex pattern is asserted in CI to compile successfully under `RegexBuilder::size_limit(N)`, the same conservative `N` used at runtime (§11.3) — **not** a wall-clock "bounded-time" check, which an earlier draft specified and which is the wrong tool: `size_limit`/`dfa_size_limit` bound *compiled program size in bytes*, not compile time, and a timing-based CI assertion would be machine- and load-dependent (flaky on a busy runner, passing on a fast one) — exactly the wrong property to gate a merge queue on. A deterministic size-bounded compile assertion tests precisely the property the runtime mitigation (§11.3) relies on. A pattern that fails the compile-under-size-limit check fails CI, not silently degrades at runtime.
- Timeout/deadline behavior (§2.1) has dedicated tests: a backend that never returns must not hang `detect`/`scan` past its configured deadline.

### 8.1 Evaluation corpus and calibration (prerequisite for tuning any threshold)

No detection threshold in this spec — `QUORUM`, per-family `Suspicious`/`Strong` cutoffs, the eventual `MlPerplexity` calibration in §7 item 4 — ships with a real number behind it without this existing first. Before those constants are finalized:

- Assemble a held-out labeled corpus of known-human and known-AI text (starting point: the existing `nobots` rubric/fixtures, extended with fresh samples across multiple LLM generations, since vocabulary tells are time-bound and generation-specific per the research corpus).
- State an explicit target false-positive rate on human text — this is a product decision (what FPR is acceptable for a linter vs. an accusation-grade tool), not something to leave implicit.
- Every threshold constant in the codebase (`QUORUM`, family-level cutoffs, eventually the perplexity ratio threshold) is tuned against this corpus and the FPR target, not hand-picked, and re-run whenever the corpus grows.
- This calibration pass is what determines whether `QUORUM = 2` is actually right for the default build's three-family quorum (§2.4) — the constant is a starting point, not a conclusion, even though it's also the Python's validated starting point.
- **The corpus has a shelf life and needs a refresh cadence, not a one-time build.** §8's own premise — "vocabulary tells are time-bound and generation-specific" — means a corpus built from today's model generations stops being representative as newer models ship; thresholds tuned against a stale corpus decay silently rather than failing loudly. Corpus refresh (and re-tuning every threshold constant against the refreshed corpus) is an ongoing maintenance commitment — a starting cadence of roughly annual refresh, revisited if new model generations ship faster than that in practice.

## 9. Key open items carried into implementation planning

These are empirical or due-diligence items the plan should sequence early, since they affect architecture decisions downstream:

1. **Prototype candle + `desklib/ai-text-detector-v1.01`** as the first concrete step of the `classifier` tier — the `debertav2` module's existence is confirmed, but nobody has been found to have actually loaded that specific checkpoint into it. `ort` + ONNX export is the documented fallback if it doesn't work cleanly. **At the same priority:** verify the checkpoint's own license (separate from the Rust crates that load it — model weights carry their own, often more restrictive, license terms) permits nobotrs's intended use, before prototyping past a spike. Do the same license check for whatever perplexity-tier model pair is ultimately chosen.
2. **Downloaded model weights are checksum-verified against a pinned hash before load**, for both the `classifier` and `perplexity` tiers — a supply-chain integrity requirement, not just a correctness nicety.
3. **Validate `postagger.rs` accuracy** against a labeled sample before trusting it in any verdict, if/when POS features are picked back up.
4. **The CC BY-SA/MIT question (§11) was framed around the wrong legal question in earlier drafts, and re-framing it changes the urgency and the actual blocker.** Two prior drafts treated this as "does embedding CC BY-SA content in a binary obligate the binary itself under CC BY-SA?" and gated the first tagged release on getting that answered. That framing mostly dissolves on inspection: **a copyright holder is not bound by its own outbound license.** If nobotrs holds copyright in the dictionary's content, it can publish `dictionary/` to the world under CC BY-SA 4.0 *and* embed the identical content in its own MIT binary under its own retained rights (equivalently: dual-license the data as `CC-BY-SA-4.0 OR MIT`) — ShareAlike constrains downstream redistributors, not the original licensor. Compile-time embedding (§11.4's original design — `include_str!`, single-file binary, works everywhere including `cargo install`, no extra install step) is available on this basis without waiting on a legal opinion about binary-derivative-work status specifically. (This is not a substitute for real legal review before release — see below — it's a correction to what that review should actually be checking.)

   **The real, time-sensitive blocker this reframing surfaces: inbound contributions.** §11.5 explicitly invites external dictionary contributions. The moment a third party's entries are accepted, nobotrs is no longer the sole copyright holder and cannot unilaterally dual-license the embedded copy anymore — this must be decided **before** §11.5's contribution process opens, not after, via either a CLA or a stated inbound license requirement in `dictionary/README.md` (e.g., "by contributing, you license your contribution under `CC-BY-SA-4.0 OR MIT`," mirroring the outbound terms). Without this, the project accumulates entries it can't legally keep dual-licensed, and finding out after the fact means either stripping contributed entries or renegotiating with contributors retroactively.

   **A separate, unresolved question worth surfacing rather than deciding here:** individual words and short phrases are not independently copyrightable subject matter in most jurisdictions (e.g. 37 CFR 202.1(a) in the US); a curated word/phrase list attracts, at most, thin "selection and arrangement" copyright over the collection as a whole. This means CC BY-SA's ShareAlike protection may be substantially weaker than §11.1 assumes — and Creative Commons' own guidance steers people away from CC licenses for software/data specifically, toward CC0 or ODbL (Open Database License) for exactly this kind of structured dataset. **This is flagged for awareness, not applied as a change** — the project owner chose CC BY-SA 4.0 deliberately, and this spec does not override that choice; it's included here so the choice is made with the caveat in view, and so a real legal review (still recommended before release, per the original intent of this item) covers copyrightability specifically, not just the binary-embedding question this item originally over-focused on.
5. **Establish an explicit fallback preference order across `candle`, `ort`, and `llama-cpp-2`, tested per target platform in CI** — not just documented as "candle first, ort as fallback" (§2.2) with no verification that both paths actually work identically. A binary distribution where `classifier` silently uses a different backend on Windows than on Linux because of a missing system library is a non-deterministic UX bug users would discover by accident, not by design. CI needs a distinct build/test job per platform × backend-path combination this fallback can take.

**Second correction: the pure-Rust LZMA crate is `lzma-rs`, not `xz`.** An earlier draft named `xz` (v0.4.x, `youknowone/xz-rs`) — checked directly against crates.io, the license claim (MIT OR Apache-2.0) and "genuine pure-Rust fork of `xz2`" characterization are both correct, but only a pre-release (`0.4.6-rc.0`) exists in that line; a normal `xz = "0.4"` `Cargo.toml` requirement will not resolve, since Cargo excludes pre-releases from ordinary version requirements by default. `lzma-rs` (0.3.0, stable, ~33M downloads, also pure Rust, MIT) has no such problem and is the corrected recommendation used in §2.2's table. Separately: `check_ai_tells.py` computes its compression ratio at `lzma.compress(raw, preset=6)` — **the ratio is meaningless without its preset**, since a threshold calibrated at preset 6 doesn't transfer to a different preset. The hand-rolled Rust implementation must pin the same preset (6) alongside whatever threshold §8.1's calibration produces, and similarly the hand-rolled MTLD implementation must match the Python's specific parameters (a TTR factor threshold of 0.72, and MTLD's standard forward-plus-reverse-pass averaging) rather than a plausible-looking reimplementation that happens to diverge — this is exactly why §8's reference-test-vector requirement exists, and naming these two specific parameters here makes that requirement concrete rather than aspirational.

**The one deliberate exception to "everything is MIT/Apache-2.0/Unlicense" is the tell dictionary (§11), which is CC BY-SA 4.0 by design** — a separate, independently-licensed data artifact, not a code dependency, kept in its own subdirectory with its own LICENSE file specifically so this exception is unambiguous rather than silently mixed into the crate's license story.

## 11. Tell dictionary (separately licensed)

The word/phrase tell list ships as its own artifact, `dictionary/`, licensed **CC BY-SA 4.0** — distinct from the rest of the repository (source code, MIT, root `LICENSE`). This is the one place in the project where two licenses coexist by design, called out explicitly in §10.

### 11.1 Why a separate license

A curated word/phrase list is a creative/curatorial dataset, not source code — CC BY-SA 4.0 is the standard choice for this kind of lexical resource. Its ShareAlike clause ensures downstream forks/derivatives of the *dictionary* stay open and attributed, which isn't a concern the MIT-licensed code needs or benefits from. Keeping the two licenses in separate directories with separate `LICENSE` files avoids ambiguity about which terms apply to which files — there is never a file where both licenses could plausibly apply.

### 11.2 Location and contents

- `dictionary/LICENSE` — full CC BY-SA 4.0 text.
- `dictionary/README.md` — states the license, attribution requirements, schema documentation, and (per §9 item 4) the inbound contribution license requirement, stated before any external contribution is accepted.
- `dictionary/entries.json` — **one file, not two.** An earlier draft named separate `words.json`/`phrases.json` files in this section while §11.3 simultaneously specified a single JSON document (one `entries[]` array holding both `kind: "word"` and `kind: "phrase"` records) — those can't both be right, and this resolves it in favor of the single-document schema §11.3 already details, since splitting by file would make the `kind` field on each entry redundant. Plain JSON (broadest cross-language consumability; no Rust toolchain required to read it).
- **`Punctuation` (§2.2) has no representation in this file at all** — it's a count over the text (em-dash/mechanical-punctuation density), not a match rule, so it's implemented entirely as code within the `deterministic` tier's `Punctuation` backend, not as dictionary entries. Stated explicitly here since the dictionary's scope-boundary paragraph below previously carved out the three structural patterns but not this.
- A root-level `NOTICE` file states plainly that the repository contains two independently licensed components (code: MIT, root `LICENSE`; dictionary: CC BY-SA 4.0, `dictionary/LICENSE`). Anyone redistributing the *dictionary content itself* (forking/republishing the JSON) has ShareAlike/attribution obligations distinct from the code's MIT terms. §11.4 below describes how the binary consumes it.

### 11.3 Entry schema (rich records, per product decision)

```json
{
  "schema_version": "1.0.0",
  "dictionary_version": "2026.07.26",
  "entries": [
    {
      "id": "delve",
      "kind": "word",
      "match_type": "exact",
      "pattern": "delve",
      "variants": ["delves", "delving"],
      "case_sensitive": false,
      "whole_word": true,
      "family": "Vocabulary",
      "category": "vocabulary",
      "suggested_replacements": ["look into", "explore", "start"],
      "model_era": ["gpt-3.5", "gpt-4o"],
      "source": null,
      "notes": null
    },
    {
      "id": "not-just-x-but-y",
      "kind": "phrase",
      "match_type": "regex",
      "pattern": "it'?s not just [a-z ]+, it'?s",
      "case_sensitive": false,
      "family": "Vocabulary",
      "category": "structural-phrase",
      "suggested_replacements": [],
      "model_era": [],
      "source": null,
      "notes": "negative parallelism"
    }
  ]
}
```

`match_type` tells the `deterministic` tier (§2.2) which matcher to use: `exact` entries feed `aho-corasick`; `regex` entries feed the `regex` crate. `family` maps the entry to a `SignalFamily` (§2.1) explicitly — in v1 every dictionary entry's `family` is `Vocabulary` (the only dictionary-driven voting family; `Punctuation` is code-only, §11.2), stated explicitly here because the earlier draft left the entry-to-family correspondence to be inferred from `category`, which doesn't actually name a `SignalFamily` variant (`"structural-phrase"` maps to neither `Vocabulary` nor anything else by name) — `category` is descriptive/organizational metadata for humans browsing the dictionary, `family` is what the aggregator (§2.4) actually reads. `suggested_replacements` feeds `lint`'s `Evidence.suggestion` (§3) directly for word-kind entries — the mechanism §3 refers to as sourced "from the tell dictionary." `model_era` is optional metadata (populated over time, not required at v1 launch) reflecting the research finding that vocabulary tells are time-bound and generation-specific; it is not currently consumed by aggregation (§2.4) but is reserved for a plausible future per-era weighting refinement.

**Two fields load-bearing enough that their absence would be a bug, not just a gap — corrected from an earlier draft that omitted both:**
- **`case_sensitive: bool` (default `false`).** The seed list this dictionary is ported from compiles every pattern with `re.IGNORECASE` (`check_ai_tells.py`) — without an explicit field, sentence-initial matches ("Delve into…") would be a coin flip on whatever an implementer happened to pick. The worked phrase example above previously omitted this field entirely, which meant it would fail to match its own most common real-world occurrence (sentence-initial "It's not just…") — that's now fixed by the `"case_sensitive": false` shown above, and generalizes: every entry ported from the seed list needs this field set to match the seed's actual behavior, not silently default to something stricter.
- **`whole_word: bool` (default `true`), exact entries only.** `aho-corasick` is a substring matcher, not a word-boundary-aware one: an `exact` entry for `"harness"` without word-boundary semantics matches inside `"harnessed"`, `"era"` matches inside `"operation"`, `"foster"` matches inside `"Foster"` (a name) — a false-positive generator on `Vocabulary`, the family that fires most often. The Python seed list's `\b...\b` regex boundaries are the semantics this field restores.

**`variants`** groups morphological forms (delve/delves/delving) under one entry sharing one `id`, one `family`, and one set of `suggested_replacements`, rather than requiring three separate entries (or a regex, which would then need `match_type: "regex"` and lose `aho-corasick`'s speed advantage for what's fundamentally still exact matching).

**Matcher configuration this schema requires but doesn't itself state:** the longest-match-wins rule below requires `aho-corasick` to be configured with `MatchKind::LeftmostLongest` specifically — its default (`Standard`, leftmost-first) does not implement "longest wins," and the cross-engine merge between `aho-corasick`'s match set and `regex`'s match set needs its own defined step, since the two matchers run independently and don't share a match-resolution pass by default.

**Conflicting/overlapping suggestions.** If two entries match overlapping spans of text (e.g. a `"delve"` entry and a `"delve into"` phrase entry both matching "delve into the details"), `lint` needs a defined priority rule rather than emitting two contradictory suggestions for the same text: **longest match wins.** The narrower entry's match is suppressed when it's fully contained within a longer match from another entry; this is a simple, deterministic rule that doesn't require entry-authoring-order to matter (a property worth preserving given the dictionary is meant for external contribution, §11.5).

**Regex entries and compile-time cost.** Because the dictionary accepts external contributions and its `regex`-kind entries are compiled at runtime via `regex::Regex::new()`, a poorly-formed pattern (nested repetitions, large character classes) can be expensive to *compile* even though the `regex` crate guarantees linear-time *matching* — this is a real, crate-documented resource-exhaustion vector (see §8's CI requirement), not a theoretical one. Mitigations: every dictionary regex is asserted in CI to compile successfully under a conservative `RegexBuilder::size_limit(N)` (§8 — a deterministic size bound, not a wall-clock timing check, which would be flaky) before it can be merged, and the same `size_limit(N)` is applied at runtime, so a pattern that somehow slips past CI still fails safely (the entry's `Vocabulary` family vote treats a compile failure as `Abstained`, not a panic or a hang).

**Scope boundary:** the dictionary covers word- and phrase-level tells expressible as an exact string or a regex pattern. The three structural patterns identified during prior-art review (`docs/research/09-no-ai-slop-review.md`) — colon-reveal, negative-listing, markdown formatting-slop — are not all cleanly regex-expressible (formatting-slop in particular requires counting/structural logic, not string matching) and are therefore implemented as code-level checks within the `deterministic` backend, not as dictionary entries, even though negative-listing and colon-reveal may end up regex-representable in practice. This keeps the dictionary schema honest: an entry describes a match rule any consumer, in any language, can apply directly from the JSON — not a rule that requires nobotrs's specific code to interpret.

### 11.4 Consumption

nobotrs embeds `dictionary/entries.json` at compile time (`include_str!` / a small `build.rs`), so the shipped binary stays single-file and works fully offline everywhere, including `cargo install`, with no extra install step — this reverts to the original design after §9 item 4's reframing: the licensor-not-bound-by-its-own-license reasoning there means compile-time embedding doesn't need to wait on a binary-derivative-work legal opinion the way earlier drafts assumed. **What compile-time embedding does need, and must have before §11.5's contribution process opens, is the inbound-licensing decision from §9 item 4** (a CLA or a stated dual-license requirement in `dictionary/README.md`) — without it, an accepted third-party contribution silently breaks the assumption that nobotrs can freely embed the whole file.

The JSON file in `dictionary/` remains the canonical, independently fetchable source regardless: any tool, in any language, can read it directly from the repository without depending on nobotrs. Publishing the dictionary to a stable CDN URL or a package registry (npm/PyPI-style, for easier non-Rust consumption than "clone the repo") is a plausible v2 addition, not committed to for v1.

### 11.5 Versioning

The dictionary carries its own `schema_version` (format stability, mirroring §3's JSON output `schema_version` pattern) and `dictionary_version` (content revision, independent of the nobotrs crate's own semver) — the two evolve on different cadences: the schema should rarely change, while entries get added/refined much more often as new model-era vocabulary tells are identified. Seed content: `check_ai_tells.py`'s existing word/phrase lists, plus the vocabulary/phrase findings from `docs/research/09-no-ai-slop-review.md` (facilitate, empower, robust, cutting-edge, paradigm shift, harness; "here's the thing," "let me be clear," "the uncomfortable truth is," "experts agree," "studies show," "that's it, that's the [x]").

`candle` is pre-1.0 — no MSRV/pinning policy is stated here yet; pin an exact version in `Cargo.lock` and revisit pinning strategy once the `classifier`/`perplexity` prototypes (§9) are underway. Rust edition and MSRV otherwise follow current stable Rust at implementation start, stated explicitly in `Cargo.toml` rather than left implicit. A single-crate-with-features layout (not a Cargo workspace split) is sufficient for v1, consistent with research report 05's conclusion — revisit only if the optional heavy dependencies start causing real build-graph friction in practice. `nobotrs` makes no telemetry or usage-data calls of any kind; this follows directly from the local-first goal in §1 but is stated here explicitly rather than left to be inferred.
